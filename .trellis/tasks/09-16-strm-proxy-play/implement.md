## 集成验收步骤

在**全部子任务完成后**, 由开发者在真实环境执行:

### V1 链路方向核验（AC1）

1. 用命中前缀的 strm 播放一个视频。
2. 在部署本项目的服务器上确认出站连接:
   ```bash
   ss -tnp | grep 7811        # 或对应上游端口
   ```
   应能看到本项目进程到上游的 ESTABLISHED 连接。
3. 确认客户端没有直接连上游: 在客户端侧（或上游侧日志）确认连接来自本项目服务器 IP。
4. 确认 Emby 进程没有产生到上游的连接。

### V2 Range / seek 核验（AC2）

1. 播放中拖动进度条到视频中后段。
2. 日志中应出现递增的客户端 Range 与对应的上游 206。
3. 画面正确跳转, 无长时间卡顿、无从头重播。

### V3 内存与并发核验（AC3 / AC8）

部署机器内存小于 1GB（C9），这是本项验证的硬约束。

1. 播放一个 600MB 以上的文件, 持续 2-3 分钟并多次拖动。
2. 观察 RSS:
   ```bash
   ps -o rss= -p $(pgrep -f go-emby2openlist)
   ```
   不应出现与文件大小同量级的跃升（百 MB 级）。对照组: 改动前播放同样文件的内存曲线。
3. 并发播放 2-3 个不同视频, 内存仍应平稳。预期增量在 MB 量级 —— 每路流约 128KB（`design.md` §11），若观测到远高于此的增量, 说明某处仍在整体缓冲, 需要排查而不是调参。
4. 从日志还原并发规模:
   ```bash
   grep -E '\[直链代理\] (当前活跃传输|传输完成|传输中断)' <日志>
   ```
   确认 L14 的活跃数符合实际播放路数。若接近或触发了 `max-concurrent-streams` 的等待（L13）, 记录实际并发峰值, 据此决定是否调整默认值 16 —— 不要凭感觉调参, 以这条日志为准。

### V4 日志可排查性核验（AC4）

```bash
grep '\[直链代理\]' <日志>
```

一次正常播放应能还原出 L1 → L9 的完整序列（条目定义见 `design.md` §7）。人为制造一次失败（例如临时改错域名）应能看到明确的 Error 而非静默失败。

| 用例 | 期望 |
|---|---|
| 未命中前缀的 strm 地址 | 仍返回 302, 日志只有一条 `未命中任何代理前缀` |
| 本地媒体播放 | 与改动前一致（同源 307 / 异源代理回源） |
| 字幕接口 | 与改动前一致 |
| 图片接口 | 与改动前一致 |

## 回滚点

> **本仓库不做 git 提交**（开发者明确要求: 这是上游项目的本地副本, 改动只留在工作区）。
> 因此**不能依赖 `git revert`** —— 工作区里会同时累积多个子任务的改动, 无法按提交粒度回滚。
>
> 远端是干净基线（HEAD = `d697fec`）, 回滚手段按优先级如下。

| 回滚点 | 方式 | 说明 |
|---|---|---|
| 功能不符合预期但代码正确 | `emby.strm.proxy.enable: false` | **首选**。无需改代码、无需回滚任何改动, 立即回到改动前行为 |
| 回滚第 N 个子任务 | `git checkout -- <该子任务改动的文件>` + 删除该子任务新增的文件/目录 | 四个子任务的文件集基本互斥（见下表）, 因此按文件回滚可行 |
| 回滚全部 | `git checkout -- .` + 手动清理新增文件与目录 | 回到 HEAD 基线 |

各子任务的文件集（用于按文件回滚）:

| 子任务 | 改动的已有文件 | 新增的文件/目录 |
|---|---|---|
| ① `cache-stream-passthrough` | `internal/web/cache/{cache.go,type.go,holder.go}` | `internal/web/cache/cache_internal_test.go` |
| ② `strm-proxy-core` | `internal/config/emby.go`、`config-example.yml` | `internal/service/streamproxy/` |
| ③ `strm-proxy-integration` | `internal/service/emby/redirect.go` | 无 |
| ④ `remove-openlist` | 多个（见该子任务 `prd.md` 的清单） | 无（只删） |

**顺序约束**: ③ 依赖 ① 与 ②; ④ 必须排在 ③ 之后（它与 ③ 改同一批文件, 功能未验证稳就动会分不清问题来源）。

**恢复原文件**: 被删除的文件用 `git checkout -- <path>` 即可从 HEAD 恢复 —— 这是不做提交的前提下唯一可靠的"撤销删除"手段, 因此 ④ 执行前建议先确认工作区状态。

## 风险与关注点

| 风险 | 观察方式 | 应对 |
|---|---|---|
| 上游并发连接限制 | 播放时上游出现 429/连接被拒 | 引入单飞（`singleflight`）合并并发解析; 必要时限制并发连接数 |
| 上游 IP 白名单未包含本项目服务器 | 上游返回 403 | 需用户在网关上加白本项目服务器 IP |
| 带宽成为瓶颈 | 播放卡顿, 本项目服务器出/入带宽打满 | 属架构固有代价（PRD Background）, 需要用户确认服务器带宽可承受 |
| 小内存机器被非代理因素吃满 | RSS 高但并发播放数很少 | 代理流本身仅约 128KB/路, 不会是原因; 排查 Emby 接口缓存、转码残留与运行时基线 |
| HEAD 请求被全局短路（Q2） | 某客户端探测文件大小失败 | 若确有客户端受影响, 单独立任务处理 |
| 上游未来改成返回 302 | 日志出现 L6 跳转记录 | 实现已兼容, 无需改动 |
