# strm 直链代理播放(客户端流量走本项目)

> 父任务。本文件持有**需求全集**、**子任务地图**与**跨子任务验收标准**；
> 各子任务的实现细节、验收项和回滚点写在各子任务自己的 `prd.md` / `implement.md` 中。
> 技术契约（配置 schema、匹配规则、日志格式、错误语义）统一记在本目录 `design.md`。

## Goal

strm 文件内容是一个 http 地址且以**用户配置的域名/前缀**开头时, 由部署本项目的服务器**主动请求该地址**, 并在本机完成字节流代理, 直接把数据推送给客户端播放。**不再返回 302** 让客户端自己去连。

同时: 上述每个环节都要有固定格式、可直接 grep 的日志, 供开发者验证链路和排查问题。

## Background

### 改前链路

```
客户端 ──► 本项目 ──► Emby            (PlaybackInfo / Items / 等接口)
客户端 ──► 本项目 ──(307 Redirect)──► 上游直链地址   (媒体数据, 不经过本项目)
```

`internal/service/emby/redirect.go:95-106` 在识别出 `MediaSources[].Path` 是 http 远程地址（strm）后, 用 307 把客户端甩到目标地址。

### 改后目标链路

```
客户端 ──► 本项目 ──► Emby            (元数据/接口, 不变)
客户端 ◄─► 本项目 ◄─► 上游直链地址     (媒体数据, 本项目代理)
```

Emby **完全不参与**媒体数据传输。客户端后续所有请求（含拖动进度的 Range 请求）始终指向本项目。

### 为什么要代理而不是 302

上游网关只对部署本项目的服务器开放（IP 白名单 / 内网可达），客户端无法直连。此外也可避免把上游地址暴露给客户端。这个前提决定了"代理失败时回退 302"通常是无效回退。

## Evidence

上游实测与代码风险分析见同目录 `research/strm-proxy-findings.md`。三条结论直接影响需求：

| 编号 | 结论 | 依据 |
|---|---|---|
| E1 | 上游 `/redirect` 端点**不返回 302**, 直接 `200 OK` 流式返回文件；带 Range 返回 `206` + 正确的 `content-range` | 2 次真实探测, 见 findings §2 |
| E2 | 沿用 strm 原文发请求会生成**畸形 HTTP 请求行**（裸空格截断请求目标），Go 不报错 | 本地 Go 1.26.3 复现, 见 findings §3 |
| E3 | 响应缓存中间件会**把整个响应体缓冲进内存**, 且 `Reg_ResourceStream` 在白名单内 | 代码分析 + `cache.go:73` 的跳过判断早于 writer 包装, 见 findings §4 |

E1 使"解析直链"这一步在本例中不存在；E2 要求请求前必须做 URL 归一化；E3 是本功能的**前置 blocker**, 必须先解决。

## Requirements

### 功能性

- **R1 域名匹配**: 支持配置一组 URL 前缀; strm 内容命中其中任一前缀时进入代理模式, 未命中保持现有 302 行为。
- **R2 上游请求**: 由本项目的服务器发起请求, 不使用客户端 IP, 不走 Emby。请求前必须对 URL 做归一化与安全编码（对齐 E2）。
- **R3 兼容 3xx 与 2xx**: 上游返回 3xx 时跟随重定向直到拿到最终地址（受最大跳数限制）, 再对最终地址发起带 Range 的请求; 上游直接返回 2xx 时不做额外解析。两条路径对客户端表现一致。
- **R4 流式代理**: 以流式方式把上游响应体写回客户端, 全程不整体缓冲进内存。必须支持 Range/206、Content-Length、Content-Range 的正确透传, 使客户端可拖动进度。
- **R5 直链缓存与失效重试**: 直链解析结果进内存缓存（时长可配, 默认 10 分钟）; 上游返回"直链失效"类状态码时清除缓存并重试一次。
- **R6 客户端断连处理**: 客户端中断播放时, 上游连接必须随之释放, 不得继续拉取剩余数据。
- **R7 全链路日志**: 从"识别出 strm 远程地址"到"传输完成/中断"的每个决策点与失败点都有日志, 带固定前缀便于 grep。具体条目见 `design.md` 的日志契约。
- **R8 移除 OpenList 功能**: 本项目不再需要 OpenList 相关的任何能力。
- **R9 并发控制与观测**: 提供可配的并发传输上限（默认 16, `0` 为不限）, 满载时等待而非拒绝; 每次传输的活跃数与字节数可从头日志还原。**注意: 该能力的目的不是内存**（每路流仅约 128KB, 见 `design.md` §11）, 而是防止打满上游连接数与本机带宽。

### 非功能性

- **R10 默认关闭**: 新功能通过配置显式开启; 未配置时行为与改动前完全一致。
- **R11 不破坏既有能力**: 未命中的 strm 地址、本地媒体、转码、字幕、图片等既有路径行为不变。

## Constraints

- **C1** 所有出站 HTTP 必须走 `internal/util/https`（全局 client + `RequestHolder`），禁止裸 `http.Get`。
- **C2** 测试只用标准库, 表驱动 + `t.Errorf`; 不得引入 testify/gomock。
- **C3** 日志走 `internal/util/logs`, 消息用中文, 不得打印 api key / token。
- **C4** 新配置项需同时更新 `internal/config/<域>.go`（字段 + yaml tag + `Init()` 校验）与 `config-example.yml`。
- **C5** 注释与错误消息用中文; 导出标识符需 godoc 风格中文注释。
- **C6** 不得新增反向依赖（`service` 不得依赖 `web`；本功能所需的缓存旁路能力属于 `internal/web/cache`，改动留在该包内）。
- **C7** `go build ./...` 需要 `web/dist` 存在（`web/embed.go` 的 `//go:embed all:dist`），干净检出需先 `./build_web.sh` 或 `mkdir -p web/dist`。
- **C8** 本地 Go 工具链在 `/usr/local/go/bin`，默认不在 `PATH`（`export PATH=$PATH:/usr/local/go/bin`）。
- **C9 部署机器内存小于 1GB**。这是硬约束, 直接决定了三件事: (a) 字节流响应绝不能进内存缓冲（子任务 1）; (b) 代理传输必须使用固定缓冲而非整体缓冲; (c) 任何新增的常驻内存结构都需要说明量级与上限。

## Cross-Child Acceptance Criteria

以下为**父任务层面**的验收, 在全部子任务完成后统一核验:

- [ ] **AC1** 播放一个 strm 内容命中配置前缀的视频, 客户端流量全程指向本项目; 抓包或上游日志确认数据由本项目服务器拉取。
- [ ] **AC2** 播放过程中拖动进度条可正常 seek（客户端发出 Range 请求 → 上游 206 → 画面跳转正确）。
- [ ] **AC3** 本项目进程内存不随播放时长/文件大小增长; 播放 600MB+ 文件时 RSS 无百 MB 级跃升（验证 E3 已解决）。
- [ ] **AC4** 日志能完整还原一次播放的链路: 命中域名 → 归一化地址 → 缓存命中/未命中 → 上游响应 → （如有跳转）→ 开始传输 → 传输完成/中断, 且可用固定前缀一键过滤。
- [ ] **AC5** 未命中配置前缀的 strm 地址、本地媒体、字幕、图片接口行为与改动前一致（**例外**: 字节流路由不再参与响应缓存, 见下方"已知行为差异"）。
- [ ] **AC6** 关闭新功能开关后, 代码路径与日志输出与改动前一致（回退安全）。**注意**: 开关关闭**并不**让字节流路由恢复响应缓存 —— 那是子任务 ① 的无条件改动, 见下方"已知行为差异"。因此这里验收的是"策略与代码路径一致", 而非"逐字节一致"。

### 已知行为差异（实现阶段发现, 必须如实记录）

**字节流路由的响应缓存被无条件移除, 与 `strm.proxy` 开关无关。** 连带后果:

| 受影响的功能 | 改动前 | 改动后 |
|---|---|---|
| `strm.internal-redirect-enable: true` 且上游**可达** | 302 响应被缓存 10 分钟, 上游探测每 10 分钟一次 | 每个请求都重新探测 |
| `strm.internal-redirect-enable: true` 且上游**不可达** | 10 分钟内只做一轮探测（内部 `trys.Try` 3 次、间隔 2s） | **每个请求**都重跑一轮, 最坏单请求增加约 4s 延迟; 播放器的多次请求会逐次叠加 |
| `strm.internal-redirect-enable: false`（默认值） | 无影响 | 无影响 |

**这份代价分析是对子任务 ① PRD 中"代价很小"一说的修正** —— 当时只算上了探测成功的路径, 漏掉了探测失败路径的放大效应。子任务 ① 已归档, 故把修正记录在此处（父任务 PRD 是跨子任务的唯一事实来源）。

**仍然维持原决策, 不为此把 stream 路由加回白名单**: 加回去会重新引入"代理 625MB 时把整个响应体缓冲进内存"的 OOM 路径, 那是本功能的前置 blocker, 代价远大于上述延迟。

**对当前部署的实际影响**: `internal-redirect-enable` 的默认值是 `false`, 因此默认配置下无影响; 仅在开发者显式开启该选项、且存在上游不可达的 strm 地址时才会遇到。
- [ ] **AC7** 移除 OpenList 后 `go build ./...` 与 `go vet ./internal/...` 通过, 剩余功能可用。
- [ ] **AC8** 日志可还原任意时刻的并发传输规模（L14 的活跃数 + L9/L9' 的字节数与耗时）, 并据此确认 `max-concurrent-streams` 默认值 16 在真实使用中是否需要调整（R9）。

## Out of Scope

- OpenList 之外的其它网盘直链适配。
- 转码 / m3u8 播放链路的代理（本任务只覆盖直链直连播放）。
- 客户端播放器兼容性适配（`DeviceProfile` / 转码策略等）。
- `internal/web/handler.go:21` 对所有 HEAD 请求返回空 200 的既有行为（见开放问题 Q2）。
- 上游网关本身的行为修改。

## Open Questions

- **Q1** 用户后续的 strm 链接是否都指向同一网关? 是否存在返回 302 的分支?（当前按 R3 同时兼容, 不阻塞）
- **Q2** 是否需要支持 HEAD 请求透传到上游? 现状是所有 HEAD 被 `globalDftHandler` 短路成空 200。若播放器依赖 HEAD 探测文件大小, 可能需要单独处理。
- **Q3** 上游网关是否有并发连接数限制? 播放器会并发开多条 Range 连接。
- **Q4** 代理后上游看到的客户端 IP 变成本项目服务器 IP, 需确认上游白名单已包含该 IP。
