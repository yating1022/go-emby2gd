# design：预取流式化与让路（v0.3.2）

## 1. 动机（2026-10-10 用户实测日志证据）

- 《监所男子囚生记》E01–E04：每集首触预取 **26–30s**。拆解：8×4MB 头块 + 尾块 = **~10 次独立请求**；Google 对每个新请求有 ~1s 固有初始化（10 次 ≈ 10s 纯开销）+ 小块请求在慢线路上只有 ~1.3MB/s（而单条大流实测 5–12MB/s）。
- 用户秒点播放：预取才刚开始，只有块 0 可用 → E02 起播 ~8s（有改善但远未到极限）。
- 网关预热 WARN `读取预热响应失败: context deadline exceeded` 为**假告警**：触发已送达（节点收到请求即开始预取），仅响应体读取超时。

## 2. 变更（全部在 `agent/internal/proxy/prefetch.go` + 网关 `internal/service/emby/preheat.go`）

### 2.1 头预取改为「单条大流 + 流式切片」（核心）

- 一次 `Range: bytes=0-(head_bytes-1)` 请求（沿用既有 `request()`——206 校验、401/403→Refresh 单次重试语义全部保留）；
- 边读边按 `blockSize` 切片，**每凑满一块立即 `Put`**——块 0 在收到第一个 4MB 时就绪，不再等整段头预取；日志新增 `预取: 首块就绪`（fileID、耗时、字节）；
- 上游短读（EOF 提前到）/忽略 Range 返回 200（起点非 0）→ 按已收字节尽力填块 + 记为未完成（交给 §2.3 续取）；**绝不把不完整块写入缓存**（块粒度完整性 = 既有 `readRangeBody` 的精确读语义）。

### 2.2 让路（协作式）

- `Prefetcher` 增加 `ClientBegin/ClientEnd(fileID)`；`Handler.serve()` 在进入缓存分支/透传前登记、离开时注销（仅 GET）。
- 预取的流式读取循环每 ~1MB（或 250ms）检查：**同文件有客户端请求在途 → `sleep 500ms` 再查**，直到空闲才继续读。不设硬上限（长播放期间预取静默等待；流结束后自动继续——设计记录）。
- 尾预取同样受让路约束。

### 2.3 断点续取

- 触发条件从「无任何块」改为：**期望块集（头块 0..H-1 + 尾块）存在缺失，且无在途预取**；
- 续取只抓缺失部分：头段找第一个缺失块 i，开一条 `Range: bytes=i*blockSize-(head_end-1)` 的流（连续缺失一次流完成）；尾块缺失单独一条；
- 期望块集由 `meta.size` + 配置确定性推出，**不加新持久状态**（进程内即可）。

### 2.4 网关预热假告警修复（`preheat.go`）

- 拿到响应后**不读 body，直接 `Close()`**（触发语义已完成，body 读不读无意义；也顺手省流量与连接占用）；
- 超时语义：**请求未送达**（dial/连接类错误）→ WARN「预热请求发送失败」；**已送达后**的读取/超时 → INFO「预热已触发（响应超时，节点侧预取不受影响）」。
- 超时值 8s 保持（只用于头部等待；发送成功即语义达成）。

## 3. 测试

- **块 0 早熟**：假上游慢速滴流（如每 100ms 128KB）→ 断言块 0 在流结束前已可 `Get`，且 `首块就绪` 日志先于 `预取完成`。
- **让路**：客户端请求在途时，预取上游的读取暂停（hook 上游记录读取时间线；或断言在让路期无新字节落块）；客户端结束后恢复。
- **续取**：头预取中途 kill（hook 上游截断）→ 断言已齐块保留、未齐块缺失；再次触发只补缺失块（上游请求数精确：1 条续流 + 尾）；全齐后不再触发。
- **短读/EOF/200 忽略 Range** 边界；**字节一致性矩阵**（既有）在新流式预取下全绿。
- 既有预取用例的上游请求数断言更新（10 次 → 2 次量级）；`-race`、`-count=3`。
- 网关：（httptest 假 agent）响应体立即关闭、超时语义分级日志用例。

## 4. 边界与风险

- 让路无硬上限：长播放期间预取挂起属预期；进程重启丢在途预取（缓存纯内存，自愈）。
- 单条流中断（Google 掐断）：已齐块保留 + 未完成状态 → 下次请求续取；不做流内自动重连（避免复杂度，续取覆盖）。
- 大文件头预取 32MB 一条流在极慢线路（<1MB/s）下仍需 ~30s——但块 0 与播放首段早已可用，播放体验由 §2.1 早熟+前缀先行兜底。
