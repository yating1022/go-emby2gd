# design：混合服务前缀先行（写前缀不等上游头）

## 1. 动机（2026-10-10 早实测）

- 现状（`handler.go serveCached` 混合态）：打开上游 `[start+n, end]` 请求、**等其响应头校验通过后才写第一个字节**。
- 实测：播放器首读 `bytes=0-`（前缀 32MB 已本地）TTFB 仍 1.6–3.3s、偏移重启 `635914-` 2.4s——**全部是"等上游头"的时间**（深偏移 + 同文件限速加固时更甚）。
- 目标：混合态**先把本地前缀写出去**（播放器立刻拿到起播数据），上游续传在响应内部接续。

## 2. 行为变更

混合态新顺序（`serveCached`）：

1. 判定前缀命中 `n > 0` 且请求延伸超过 `start+n`；
2. **立即**写 `206` 头（Content-Range 覆盖整个 `[start,end]`）+ 写缓存前缀 + Flush；
3. 同步打开上游 `[start+n, end]`（**放在写前缀之后、同一响应内**）：
   - 上游成功且 `206 + responseRange == (start+n, end) + 身份一致` → `io.Copy` 续传（现有校验全部保留）；
   - 上游失败 / 校验不过（忽略 Range、身份不符等）→ **不再整体回退**（头部已写出，无法改状态码）：记 WARN、关闭连接（等价网络中断；客户端自愈重试）。**这是本变更明确接受的权衡**（原先"先验后写"换来"可完整回退"，代价是每次起播都付上游头延迟）。
4. `客户端断开` 语义不变（前缀写完客户端即断开时，取消上游）。

其余三态不变：全命中纯本地；未命中纯透传。

## 3. 测试（对照更新）

- 既有 `TestCacheMixedServingIsByteIdentical`：字节一致性在新顺序下**必须仍逐字节成立**（上游正常路径）；"恰好 1 次上游请求"断言保留。
- `TestCacheMixedFallsBackWhenUpstreamIgnoresRange` / `...FallsBackWhenIdentityMismatch`：语义从"整体回退 200/完整透传"改为"**前缀已写、链路关闭**"——更新断言为：客户端收到的字节是"完整前缀 + 部分/无续传"且连接被关闭、日志含 WARN；**不得**出现"完整正确响应却谎称回退"的假象。
- 新增：`TestCacheMixedWritesPrefixWithoutWaitingUpstream`——上游响应头延迟（hook 扣住）时，客户端**仍然先收到前缀字节**（TTFB 断言：前缀首字节在"上游未放行"前到达）。
- 上游失败的既有"完整回退"用例（写首字节前失败 → 谁能完整回退？**新顺序下只有"前缀为空"的窄窗口**还能回退）——检查实现里该窗口是否仍成立并断言；不成立则删除该回退分支的测试并注释原因。

## 4. 边界

- 混合只在前缀命中才走新顺序；前缀为空（全未命中）仍是纯透传（完整可回退那套保留给这条路径）。
- 版本：随 v0.3.1 发布，四台节点升级。
